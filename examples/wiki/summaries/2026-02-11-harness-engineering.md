# 工程技术：在智能体优先的世界中利用 Codex（摘要）

OpenAI 技术人员 [[entities/Ryan Lopopolo]] 撰写的工程博客（2026-02-11），汇报其团队用 [[entities/Codex]] 在 **5 个月内从空仓库搭建出约一百万行代码的内部产品**的实践经验。这个产品已有内部日活用户和外部 Alpha 测试者，**零行人工代码**——所有代码、测试、CI、文档、可观测性和内部工具全部由 Codex 编写，从 3 人团队扩展到 7 人，吞吐量反而提升，平均每位工程师每天 3.5 个 PR，累计 1,500 个 PR 被合并。

## 核心主张

- **人类掌舵，智能体执行**：工程师的工作重心从"写代码"变为**设计环境、明确意图、构建反馈回路**
- 纪律不消失，而是从代码转移到**支撑结构**：工具、抽象、反馈回路、架构约束

## 五个关键实践

1. **让应用对智能体可读**（见 [[concepts/Agent Readability]]）
   - 应用可按 git worktree 启动，Codex 为每次修改驱动独立实例
   - 接入 Chrome DevTools MCP，Codex 可截图/导航/复现 bug
   - 本地临时可观测性堆栈（Vector + Victoria Logs/Metrics），Codex 用 LogQL/PromQL 查询
   - 单次运行常持续 **>6 小时**（人类睡觉时）

2. **仓库即记录系统**（见 [[concepts/Codebase as System of Record]]）
   - 拒绝"一个巨大的 AGENTS.md"方式——情境稀缺、指导过多变无效、立即腐烂、难验证
   - AGENTS.md 降为"约 100 行的地图"，指向结构化的 `docs/` 目录
   - 设计文档、执行计划、技术债务都版本化进仓库
   - 实现**渐进式披露**：智能体从小切入点起步，按需展开
   - linter + CI + 定期运行的 "doc-gardening" 智能体维护知识库新鲜度

3. **针对智能体可读性优化一切**
   - "智能体无法在情境中访问的 = 不存在"——Google Docs、Slack、人脑里的知识都等于零
   - 倾向于选择"枯燥技术"（可组合、API 稳定、训练集里常见）
   - 情境注入要像给新同事讲产品原则/工程规范/团队文化那样充分

4. **规范架构与不变量**（见 [[concepts/Harness Engineering]]）
   - 每个业务域严格分层：`Types → Config → Repo → Service → Runtime → UI`
   - 横切关注点（auth/telemetry/feature-flag）只能通过显式 `Providers` 接口进入
   - 约束通过**自定义 linter + 结构测试**机械强制执行（lint 本身也由 Codex 生成）
   - 原则："一旦编码，立即全局生效"——规则是倍增器
   - 口号：**当文档不够完善时，我们会将规则转化为代码**

5. **熵与垃圾收集**
   - 最初靠人工清理"AI 残渣"（每周五 20% 工时），不可扩展
   - 改为后台 Codex 任务定期扫描偏差、发起小型重构 PR，多数 1 分钟内审完自动合并
   - 类比为**垃圾回收**：持续小额还债 >> 累积后痛苦清理

## 吞吐量的新逻辑

传统工程规范在高吞吐智能体环境下会失效：
- PR 生命周期短
- 测试偶发失败靠后续重跑，不无限阻塞
- **在智能体吞吐量远超人类注意力的系统里，纠错成本低，等待成本高**——所以尽量减少阻塞门
- 低吞吐环境这样做不负责任，高吞吐环境这是正确选择

## 当前的自主水平（端到端）

给一个 prompt，Codex 可独立完成：验证仓库状态 → 复现 bug → 录制故障视频 → 修复 → 运行验证 → 录制解决方案视频 → 开 PR → 回应反馈 → 修构建失败 → 仅在需要判断时交人 → 合并。

## 未解决的问题

- 完全由智能体生成的系统，架构连贯性如何长期演变？
- 人类判断力最有价值的着力点在哪？如何把判断力编码以复用？
- 随模型能力增强，这一套系统将如何演变？

## 个人评价

这篇文章值得反复读，因为它提供了一个罕见的"规模化 agentic coding 在真实生产环境"的一手数据点。但也要带一些批判：

- **样本只有一个产品、五个月、七人团队**。一百万行代码 + 3.5 PR/天的数字看起来耀眼，但这些代码的质量、架构均匀度、真实用户价值密度都没有公开基准。
- **"零人工代码"作为限制条件本身是一种 PR 修辞**——人类在持续编写 prompt、设计 linter、维护 docs、审核 PR，这些是代码的上游。把上游工作说成"非代码"，是把工作重新标签了而已，不代表工作量真的减少。
- **很难判断成果归因**。这是 OpenAI 内部团队用自家最新模型 + 专属基建，外人同等条件下能复现到什么程度是开放问题。
- 但是，**把仓库当成智能体的"记录系统"**、**把品味编码成 lint 规则**、**把 AGENTS.md 当地图而非百科全书**这三条方法论是**高度可迁移**的洞察，独立于是否"100% AI 生成"都成立。
